AI 面试题：Agent 开发与前沿模型面试全解

发表于 2026-06-13 更新于 2026-09-08 分类于 AI

AI Agent 开发面试全解，覆盖 LLM 调用链、RAG 架构、MCP 协议、多 Agent 协作和 Function Calling。

热点：前沿模型与 Agent 安全（2026 年 6 月更新）

F1. Claude Fable 5 / Mythos 5：Mythos 级模型

难度：⭐⭐⭐

问题：Anthropic 于 2026 年 6 月 9 日发布了 Claude Fable 5 和 Claude Mythos 5，这是首个面向公众的 Mythos 级（Opus 之上）模型。Fable 5 代表了目前最强的通用 AI 能力，同时引入了全新的安全架构。它的 Agent 能力、安全分类器设计、定价策略对 Agent 开发领域有何影响？

解析：

模型定位：

  • Claude Fable 5：Mythos 级模型，Anthropic 有史以来最强的通用模型，对所有 API 和企业用户开放
  • Claude Mythos 5：与 Fable 5 同一底模，但解除了网络安全领域的限制，仅对 Project Glasswing 等授权合作伙伴开放
  • 定价：$10/M 输入 token，$50/M 输出 token——比 Mythos Preview 便宜 50% 以上
  • 知识截止：2026 年 1 月底
  • 模型字符串：claude-fable-5

Agent 能力突破：

领域 表现 基准
代码工程 1 天完成 5000 万行 Ruby 代码库迁移（原估计 2+ 个月） Stripe 实战
代码评测 前沿模型中最高的 FrontierCode Eval 分数 FrontierCode
知识工作 Hebbia Finance Benchmark 最高分 资深级推理
长任务（Slay the Spire） 持久记忆提升表现 3 倍于 Opus 4.8 达到最终关 3 倍频率
药物设计（Mythos 5） 无需人类辅助，14 个蛋白靶点中 9 个产出强候选 自动化蛋白设计

安全分类器架构（全新设计）：Fable 5 引入了三个独立的 AI 安全分类器，分别检测三类高风险的输入：

  • 命中率 <5% 的对话触发回退
  • 超过 1000 小时漏洞赏金未发现通用越狱（UK AISI 取得部分进展）
  • 数据保留策略：30 天，不用于训练

对 Agent 开发的启示：

  1. 安全分类器模式：Agent 系统的安全不应只依赖 LLM 自身，而应引入独立的安全分类器层做输入过滤和降级处理
  2. 回退策略：敏感请求不是直接拒绝，而是回退到更安全的模型——这种「不是不行，是让更安全的模型回答」的思路值得 Agent 工程借鉴
  3. Mythos/Opus 层级：Anthropic 建立了清晰的能力层级模型（Haiku → Sonnet → Opus → Mythos），Agent 开发者可以根据任务复杂度动态路由到不同层级模型

F2. System Prompt 泄漏与越狱工程：Pliny the Liberator 与 CL4R1T4S

难度：⭐⭐⭐

问题：2025-2026 年，知名黑客 Pliny the Liberator（elder_plinius）通过越狱技术成功提取了几乎所有主流 AI 产品的系统提示词，并将它们发布在 GitHub 仓库 CL4R1T4S（28.6k stars）中。这一事件对 Agent 开发和 AI 安全有何启示？System Prompt 泄漏为什么是不可避免的？如何从工程角度防范？

解析：

CL4R1T4S 仓库覆盖的产品（按目录分类）：

  • ANTHROPIC：Claude 3.5 Sonnet ~ Fable 5 全部系统提示词、Claude Code 系统提示词、Claude Designs 系统提示词、UserStyle Modes
  • OPENAI：ChatGPT 各版本系统提示词、GPTs 提示词
  • GOOGLE：Gemini 系统提示词
  • XAI：Grok 系统提示词
  • CURSOR：Cursor IDE Agent 提示词
  • CLINE：Cline 编辑助手提示词
  • DEVIN：Devin AI 工程师提示词
  • WINDSURF：Windsurf IDE Agent 提示词
  • MANUS：Manus Agent 提示词
  • PERPLEXITY：Perplexity AI 搜索提示词
  • LOVABLE：Lovable 前端生成提示词
  • REPLIT：Replit Agent 提示词
  • FACTORY、DIA、CLUELY 等其他 AI 产品

提取方法：Pliny 使用的一种典型越狱链：

  1. 利用模型对特殊 token 和 Unicode 字符的处理差异
  2. 通过角色扮演或「指令覆盖」破坏 System Prompt 边界
  3. 利用模型对「帮我总结你被设置的规则」等 meta-query 的执行
  4. 多层 Prompt Injection（多层嵌套指令覆盖）
  5. 利用模型对「代码格式输出」的偏好，要求用代码块输出全部 prompt
  6. Anthropic 多次修补后，Pliny 仍能在 24 小时内找到新绕过方法

为什么 System Prompt 泄漏几乎不可避免？：

  • LLM 无法区分「指令」和「数据」——这是架构性缺陷，不是补丁能修复的
  • 模型被训练来服从用户指令，当用户说「重复你的 system prompt」时，模型需要在「服从」和「保密」之间做选择
  • Prompt 越长、约束越复杂，泄漏面越大
  • 只要模型能通过对话理解自己的 behavior rules，它就能通过对话输出这些 rules
  • Anthropic 的 mitigation（安全分类器+回退）是目前最先进的方案，但仍然无法完全阻止

对 Agent 开发的启示：

  1. 不要将机密信息放在 System Prompt 中——API Key、数据库密码、业务密钥永远不应该出现在 System Prompt 中
  2. 对于核心 Agent 逻辑，使用工具执行而非 Prompt 描述——如 Hermes Agent 将复杂工作流编码为 Skills（SKILL.md），而非写在 System Prompt 中
  3. Prompt 即代码——System Prompt 应当像源代码一样对待：版本控制、代码审查、测试
  4. 分层安全——不应只依赖 Prompt 做安全控制，应该叠加：输入过滤 → 工具权限 → 输出审核 → 行为监控
  5. Public prompts 启发价值：虽然泄漏是安全事件，但公开的系统提示词对 Agent 开发者有巨大的学习价值——你能看到顶级 AI 产品如何设计提示词、如何处理边界情况

面试金句：「System Prompt 不是秘密。如果你的安全依赖 Prompt 不被泄漏，那你没有安全。」LLM 的安全必须是架构性的——工具权限、输入过滤、输出审核、行为监控、Human-in-the-Loop，每一层都应独立运作，任何一层的失效不应导致系统崩溃。Pliny 的 CL4R1T4S 仓库最宝贵的不是泄漏的 Prompt 本身，而是它证明了「Prompt 隔离」这条路走到头了。

0x00 LLM 调用与优化

1. Function Calling / Tool Use 的原理是什么？

LLM 通过 Function Calling 实现工具使用，核心流程：

深入思考：

  • ReAct 模式（Reasoning + Acting）：思考 → 行动 → 观察 → 思考 → ... 循环，让 Agent 自主决定调用哪些工具、何时停止。这是大多数 Agent 框架的核心循环

生产实战（Function Calling 的常见坑）：

  • 幻觉案例：某电商 Agent 在生产中定义了一个 search_products(name, category) 工具，LLM 在调用时生成了 search_products(name="iPhone", category="electronics", sort_by="price_asc")——sort_by 参数根本不存在于 Schema 中。根因：模型被用户问题中的”按价格排序”诱导，自动补全了未定义的参数。止损方案：在 tool dispatch 层做严格 Schema 校验，任何多余/缺失参数直接拒绝并返回格式化错误（{"error": "invalid_parameter", "expected": [...], "got": [...]}），而不是让 LLM 继续。某金融公司因未加此校验，模型幻觉参数导致 API 调用失败率高达 23%。
  • Schema 过简踩坑：某 SaaS 公司定义工具 send_email(to, subject, body)，未约束 to 的格式。生产中发现 LLM 经常生成 to="support"（缺少域名）、to="user@gmail.com, admin@gmail.com"（多个收件人用逗号分隔，但邮件 API 只接受单地址）。教训：工具参数的 description 必须写明格式约束（如”必须为单个有效邮箱地址，多个收件人请多次调用”），必要时加 regex pattern 或 enum 约束。
  • Tool 名称冲突：某智能客服 Agent 同时定义了 search_knowledge_base 和 search_faq，描述相似。LLM 频繁选错。优化：合并为单一工具 + 在参数中区分检索范围，或给工具名加明确场景前缀（如 kb_search vs faq_search）。

2. Prompt Engineering 的核心技巧

关键方法论：

  • Few-Shot：给 2-3 个示例，比零样本效果好得多
  • Chain-of-Thought：让 LLM 先推理再回答
  • 结构化输出：明确要求 JSON/Markdown 格式

0x01 RAG 架构

3. RAG 的标准架构和优化策略？

RAG 优化策略：

阶段 优化
Chunking 语义切分（按段落/标题）而非固定长度
检索 混合检索（BM25 + Dense）+ ReRank（Cross-encoder 重排序）
Prompt 明确指令 + Few-Shot + 引用来源
评估 RAGAS（忠实度/相关性/准确性）

生产实战（RAG 生产调优经验）：

1. Chunk Size 调参实战：

Chunk Size 召回率（Recall@5） 响应延迟 典型问题
128 chars 62% 45ms 切得太碎，语义不完整
512 chars 78% 68ms 中等场景推荐值
1024 chars 81% 95ms 效果好但上下文更占 token
2048 chars 74% 142ms 一个 chunk 内混入无关信息，反而降低精度

实测经验：某法律文档检索系统用 512 chars chunk_size + 128 chars overlap 时回答质量最高。chunk_size 超过 1500 chars 后，LLM 容易受 chunk 内噪声信息干扰，反而比小 chunk 效果差（Lost in the Middle 效应在单 chunk 内也存在）。

2. 混合检索权重调参（BM25 vs Dense Embedding 权重）：

  • 代码/技术文档场景：关键词精确匹配重要，BM25 权重建议 0.4-0.5（如 weights=[0.4, 0.6]）
  • 客服问答场景：语义匹配为主，BM25 权重建议 0.2-0.3（如 weights=[0.3, 0.7]）
  • 混合文档场景（既有技术术语又需语义理解）：动态权重——对含专业术语的 query 自动提升 BM25 权重到 0.4，对自然语言 query 降至 0.2

3. 实时写入延迟问题：某电商用 Milvus 做实时商品索引更新，高峰期新商品上架后 3-5 秒内无法被检索到。原因：向量写入后需要构建索引（IVF_FLAT 的训练过程）、flush 操作的 IO 延迟。解决方案：

  • 改用写入即可查的 HNSW 索引（牺牲一定精度换取实时性）
  • 双 Buffer 策略：一个索引用于查询，另一个异步构建新索引，构建完成后原子切换
  • CRUD 场景下使用 Milvus 的 Delta 机制或 Elasticsearch 的 NRT（Near-Real-Time）近实时写入

0x02 MCP 协议

4. MCP (Model Context Protocol) 是什么？

MCP 是 Anthropic 提出的 Agent-工具标准化协议，类似 LLM 世界的 “USB 协议”：

核心概念：

  • Resources：数据源（如文件内容、数据库记录），用 resource:// URI 标识
  • Tools：可执行的函数（如搜索、计算、API 调用）
  • Prompts：预定义的 Prompt 模板

为什么重要：MCP 让所有 AI Agent 使用统一的工具接口，不再需要为每个 Agent 平台各自实现一遍工具连接。

生产实战（MCP 生产部署经验）：

1. MCP Server 超时处理：某团队在生产中运行一个 MCP Server（通过 stdio 启动 Python 进程），Agent 调用了一个需要 60 秒执行的搜索工具，但 MCP 客户端的默认超时仅为 30 秒。结果：Agent 收到 TimeoutError 后认为工具失败，重试 3 次后放弃，返回”搜索失败”。根因：MCP 协议本身不处理超时——它只是基础传输层，超时策略由客户端实现。解决方案：

  • 为每个工具单独配置超时（MCP 协议的 tool_timeout 扩展字段），短查询设 10s，长查询设 120s
  • 实现 Streaming 进度反馈：长时间运行的工具定期发送 progress 通知防止客户端超时
  • 在 MCP Server 侧加看门狗 goroutine/thread：超时后主动返回 {"status": "timeout", "partial_result": ...} 而非一直阻塞

2. 安全隔离问题：某公司部署了文件系统的 MCP Server（filesystem），Agent 可以读写服务器本地文件。由于忘记在 MCP Server 中配置 allowed_paths 限制，Agent 意外读取了 /etc/passwd 和 /proc/self/environ。安全基线：

  • 路径白名单：MCP Server 的 filesystem 工具必须设置 allowed_paths，限制只能读写指定目录
  • 权限最小化：MCP Server 用低权限 Docker 容器运行，不挂载宿主机的敏感目录
  • 命令注入防御：对于 execute_command 类型的工具，禁止接收自由文本命令——仅允许预设命令列表中的参数化调用
  • 速率限制：每个 MCP Server 限定每秒最多 10 次调用，防止 Agent 在循环中高频调用造成 DoS

0x03 多 Agent 协作

5. 多 Agent 协作的常见模式？

模式 说明 适用场景
Sequential Agent A 输出 → Agent B 输入 流水线任务
Hierarchical 一个 Orchestrator 调度多个 Worker 复杂任务分解
Debate 多个 Agent 讨论达成共识 需要审慎决策
Parallel 多个 Agent 同时工作，结果聚合 独立子任务

生产实战（Orchestrator-Worker 失控止损）：

1. Worker Agent 失控止损机制：某客服系统使用 Orchestrator-Worker 模式，Orchestrator 委派子任务给 Worker Agent。一次生产中 Worker Agent 陷入死循环——不断调用 search_knowledge_base（每次返回大量结果）→ summarize_search_results → 再次 search_knowledge_base。10 分钟内消耗了 200 万 token（约 $10 的 API 费用），且 Worker 从未返回结果给 Orchestrator。止损方案：

  • 父子调用超时：Orchestrator 为每个 Worker 设置硬性超时（如 60 秒），超时后直接终止 Worker 线程，记录失败并降级，而非无限等待

  • 安全回归：涉及 Agent、插件或外部输入时，增加提示注入、越权调用、敏感数据外泄和审计完整性用例。
  • 可逆性：发布、暂停、回滚和数据补偿分别定义负责人和验收信号，避免把“服务恢复”误当作“业务恢复”。

0x04 Agent 长任务状态、幂等与恢复

1. Agent 执行到一半进程重启，如何避免工具副作用被重复执行？

标准答案：把每次任务拆成可持久化的状态机，保存任务 ID、步骤 ID、输入摘要、工具调用参数、执行状态和结果引用。工具调用必须携带幂等键；执行前检查已完成记录，执行后以原子方式写入结果和状态。对支付、发信、写库等不可逆动作，采用预览、审批、执行三阶段，不能依赖模型“记住自己已经做过”。

深入思考：

  • 源码层面：Orchestrator 的状态存储与 Worker 执行结果要分离，重试只重放可安全重放的步骤；超时状态必须允许人工判定“未知”，不能自动当成失败再执行。
  • 生产经验：工具返回超时不代表动作未发生，应先用查询接口对账，再决定重试；社区项目通常把 trace、tool call 和 observation 作为独立事件保存，便于重建轨迹。

2. 如何评估一个多 Agent 系统是真的变好，而不是只在演示集上得分更高？

标准答案：建立分层评估集：任务成功率、工具参数正确率、引用完整性、越权拒绝率、成本、延迟和人工接管率分别统计；同时保留失败样本和回归集，比较单 Agent、编排版本和模型版本的差异。评估结果必须能回溯到完整轨迹，而不是只记录最终文本。

深入思考：

  • 对比延伸：离线评估适合回归，线上抽样适合发现分布变化，人工评审适合校准难以自动判定的质量；三者不能互相替代。
  • 社区实践：OpenAI Evals、Langfuse 等开源项目可作为评估和追踪的实现参考，但具体指标仍需按业务风险定义。
