0x00 类型系统

1. any、unknown、never 的区别？

  • any：关闭类型检查，会污染后续推导。适合快速原型或渐进迁移
  • unknown：安全的”任意类型”。必须先类型收窄才能操作
  • never：表示永远不会发生的类型（抛出异常、死循环、穷尽性检查）

2. type 和 interface 怎么选？

维度 type interface
扩展 & 交叉 extends
声明合并 ❌ ✅（同名自动合并）
联合类型 ✅ type A = B | C ❌
元组 ✅ type T = [string, number] ❌（可用但丑）
映射类型 ✅ ❌

选型原则：描述对象形状用 interface，需要联合/交叉/映射用 type。

0x04 TypeScript 5.5+ 新特性（2024-2025 热点）

9. TS 5.5 Inferred Type Predicates 解决了什么问题？有什么限制？

TS 5.5（2024年6月发布）最受瞩目的特性——类型谓语自动推断（由社区贡献者 Dan Vanderkam 实现）。

标准答案：

在 TypeScript 5.5 之前，filter/find 等数组方法无法自动收窄类型：

核心原理：TS 5.5 会用控制流分析（Control Flow Analysis）推断函数的返回值是否为 type predicate。对于箭头函数 x => typeof x === 'string'，TS 会自动推断出返回类型为 x is string 而非 boolean。

注意限制：

  1. “当且仅当”语义：类型谓语要求 true 返回 → 参数是 T 类型；false 返回 → 参数不是 T 类型。这意味着”truthiness” 检查（如 x => !!x 或 x => x）不会触发推断，因为它们不满足”false 分支排除 T”的条件
  2. 显式注解优先：如果手动写了 : x is string，TS 不会检查一致性——你可以写 : x is number 而实际逻辑返回 typeof x === 'string'（等同于类型断言，不安全）
  3. Breaking Change：filter(x => x !== null) 现在返回 number[] 而非 (number | null)[]，可能影响依赖旧类型的代码

参考：TypeScript 5.5 Release Notes

10. TS 5.5 isolatedDeclarations 是什么？为什么需要它？

标准答案：

--isolatedDeclarations 是 TS 5.5 引入的新编译选项，要求所有导出（exports）必须显式标注类型注解，以便声明文件（.d.ts）可以完全独立于源文件生成。

为什么需要？

  • 并行构建：isolatedDeclarations 使得 transpileDeclaration API 可以在不进行完整类型检查的情况下生成 .d.ts 文件——每个文件独立处理，可以充分并行
  • 构建速度：对于大型单体仓库（monorepo），声明文件生成通常占总构建时间的 30-50%。isolatedDeclarations + --noCheck 可以将这部分的耗时降低 10 倍以上
  • 更清晰的 API 契约：强制所有导出显式标注类型，提升代码可读性

参考：TypeScript 5.5 Isolated Declarations

深入思考：

  • 适用场景：isolatedDeclarations 对库作者和 monorepo 维护者价值最大——可以显著加速 CI 构建。对于应用项目价值较小（应用代码通常不需要对外暴露声明文件）
  • 工具链兼容：tsc --noCheck --isolatedDeclarations 时，TypeScript 仅做语法转换生成 .d.ts，完全不进行类型检查。这比 tsc --noEmit 快一个数量级。在 CI 中可以拆分为：快速构建阶段（--noCheck 产出 .d.ts）+ 独立类型检查阶段（tsc --noEmit），两者并行运行

11. TS 5.6/5.7 有哪些值得关注的新特性？

标准答案：

TS 5.6（2024年9月）：

  1. Iterator Helper Methods：支持 ECMAScript 的 Iterator Helpers 提案（.map(), .filter(), .take(), .drop(), .reduce() 等方法直接作用于 Iterator 对象）

  1. --noCheck 公开化：此选项在 TS 5.5 内部使用（用于 transpileModule/transpileDeclaration），5.6 起作为 CLI 选项公开，允许构建工具跳过类型检查

  2. --build 支持中间错误：--build 模式现在允许项目引用链中有错误时仍继续构建其他项目（之前会全部停止）

  3. Strict Builtin Iterator Checks：更严格的内置迭代器类型检查

TS 5.7（2024年11月）：

  1. Computed Property Names 改进：计算属性名（[symbolMethodName]）现在会生成索引签名，而非完全忽略
  1. TypedArray 泛型化：Uint8Array、Int32Array 等现在接受泛型参数指定底层 ArrayBuffer 类型
  1. Path Mapping 改进：支持 package.json 中的相对路径重映射

面试金句：TS 5.5-5.7 的演进方向很明确——“Make TypeScript faster and stricter”。inferred type predicates 提升类型精度，isolatedDeclarations 加速构建，noCheck 让大型项目 CI 飞起来。

参考：TypeScript 5.7 Release Notes

12. TypeScript Decorators（Stage 3）与实验性装饰器有何区别？

标准答案：

TypeScript 同时支持两套装饰器系统，这导致了长期的混乱。关键区别：

维度 实验性装饰器（TS 5.0 之前默认） Stage 3 装饰器（TC39 标准，TS 5.0+）
标准 非标准，TypeScript 自行实现 TC39 Stage 3（2022年），接近标准化
启用 experimentalDecorators: true 默认启用（TS 5.0+）
参数装饰器 ✅ 支持 ❌ 不支持（从提案中移除）
元数据 emitDecoratorMetadata: true ❌ 无此功能（需等待 Reflection API）
类装饰器语法 @sealed class C {} @sealed class C {}（语法相同但语义不同）
类装饰器行为 替换构造函数 通过返回新类或修改原类
与 NestJS/Angular 兼容 ✅ ❌（这些框架依赖实验性装饰器）

关键区别：Stage 3 装饰器的 context 参数提供了丰富的元信息（context.kind、context.name、context.metadata），这是实验性装饰器没有的。

选型建议：

  • 使用 NestJS/Angular → 必须用实验性装饰器（experimentalDecorators: true）
  • 新建纯 TS 项目 → 优先 Stage 3 标准装饰器（未来兼容性更好）
  • 类库/框架开发 → 评估社区生态，目前多数框架仍依赖实验性装饰器

参考：TC39 Decorators Proposal

13. 条件类型（Conditional Types）深度实战：infer、分布式条件类型与递归类型推导

标准答案：

条件类型是 TypeScript 类型体操的核心武器。它的语法类似三目运算符：T extends U ? X : Y——如果 T 可赋值给 U，则类型为 X，否则为 Y。

深入思考：

  • 条件类型执行顺序：TypeScript 在求值条件类型时，会先延迟求值直到所有泛型参数确定——这意味着 type Foo<T> = T extends string ? true : false 在 T 不确定时不会报错，只是保持未求值状态
  • infer 的限制：infer 只能在条件类型的 extends 子句中使用，不能单独使用。而且 infer 在同一位置只能出现一次——你不能写 T extends [infer A, infer A] 来约束两个位置类型相同（需要辅助技巧）
  • 分布式条件的陷阱：type IsString<T> = T extends string ? true : false 作用于 string | number 时结果是 boolean（即 true | false），而不是 false！可以通过 [T] extends [string] 禁用分发
  • 递归深度限制：TypeScript 的递归深度默认为 50 层（可通过 --maxNodeModuleJsDepth 调整，但不推荐依赖），过深的递归条件类型会导致编译错误（Type instantiation is excessively deep）

参考：TypeScript Conditional Types

## 0x28 可暂停发布、恢复证明与策略门禁

### 1. 如何为 前端面试题：TypeScript 面试全解 设计可暂停、可恢复的变更流程？

**标准答案**：将变更拆成准备、暂停、观测、恢复和完成五个状态；暂停时冻结扩大影响的动作，恢复前重新核对产物摘要、配置、兼容窗口、权限和停止条件。恢复应生成新的变更事件并再次检查目标状态；旧版本不可用时明确选择回退、前向修复或人工接管。

**深入思考**：
- **边界情况**：暂停只控制编排器或控制面，不会自动撤销数据库写入、消息发送、缓存失效和外部副作用。
- **源码层面**：区分 desired state、observed state 和 operation state，保证重复 resume、超时重试和控制器重启不会重复动作。
- **生产经验**：把暂停是否生效、谁能恢复、所需证据和无人操作超时写进 runbook；恢复完成还要检查业务不变量和异步积压。

### 2. 如何把 前端面试题：TypeScript 面试全解 的“恢复完成”变成可验证的证据？

**标准答案**：为每次变更生成唯一 change ID，串联产物或配置摘要、主体、环境、分区、暂停/恢复/回退事件、观测窗口和验收结果。持续动作使用 trace/span，瞬时状态切换使用结构化事件，诊断信息保留为日志；完成条件同时包含技术健康度、业务指标、权限状态和未处理副作用。

**深入思考**：
- **边界情况**：监控延迟、采样或自身故障会造成“没有证据”而不是“没有问题”，关键停止和审批事件应有低依赖的最小审计通道。
- **对比延伸**：指标适合趋势和阈值，span 适合操作链路，event 适合状态点；三者不能简单混成超长日志。
- **生产经验**：证据只保存必要上下文并脱敏；对账、通知、权限和队列等跨系统结果设置最终验收，而不是只依据 HTTP 200 或 Pod Ready。

### 3. 前端面试题：TypeScript 面试全解 的发布/回退门禁如何覆盖供应链与运行时？

**标准答案**：构建阶段固定提交、依赖解析、工作流和产物摘要，生成 SBOM 与 provenance/attestation；部署和回退前验证签名、来源主体、允许的仓库或工作流、摘要及策略版本。运行时以最小权限、短时凭据、工具或网络白名单和可撤销操作限制真实影响，例外必须有审批、范围和过期时间。

**深入思考**：
- **边界情况**：attestation 证明从哪里、如何构建，不证明代码没有漏洞，也不能替代运行时授权、依赖审计和业务风险判断。
- **源码层面**：把策略版本、产物 digest 和变更 ID 作为不可变关联键，避免按可变标签或文件名选回退版本。
- **生产经验**：无法完整验证时优先切只读、限流或人工审批；不要把临时绕过门禁当成长期路径，并在事后补齐证据和轮换凭据。

## 0x1D 2026-09-03：恢复后的重新授权、业务不变量与审计证据（前端TypeScript）

### 1. 系统或任务恢复后，为什么不能直接宣布成功？

**标准答案**：恢复动作只说明控制面重新可用，不等于业务结果已经正确。应先冻结恢复范围，核对版本、配置、权限和依赖，再用业务不变量、数据完整性、积压/重试、延迟尾部和关键用户路径做分阶段验收；任何证据缺失或阈值越界都暂停扩大范围并升级人工。

**深入思考**：
- **边界情况**：进程健康、探针通过或队列继续消费，都可能掩盖重复写入、丢失事件、脏缓存和外部副作用；恢复判据必须覆盖系统之外的结果。
- **源码层面**：把恢复状态、验收阶段、变更 ID 和证据引用建模为状态机，避免“重试成功”覆盖先前的部分失败；幂等键和补偿记录要能关联原始操作。
- **生产经验**：先恢复低风险分区或影子流量，观察一段明确时间窗口，再逐步放量；无法证明安全时，优先只读、限流或人工处理。

### 2. 恢复前重新授权应检查哪些内容？

**标准答案**：重新确认调用主体、工具/接口、参数、资源范围、租户边界、凭据有效期和策略版本。授权不能只看“原任务曾经获批”，因为暂停期间身份、配置、数据范围或风险上下文可能已经变化；高影响动作保留人工审批。

**深入思考**：
- **边界情况**：短时令牌过期、权限被撤销后又恢复、重试请求携带旧参数，都会造成“恢复即越权”；恢复流程应拒绝陈旧授权并重新生成幂等执行上下文。
- **对比延伸**：最小权限、网关鉴权、运行时策略和人工接管分别控制不同边界，不能用构建来源证明替代动作授权。
- **生产经验**：把拒绝、超时、撤销、人工批准和恢复都记录成可检索事件；审计系统不可用时采用安全默认值，不因观测缺失而自动放行。

### 3. 如何让恢复决策可审计、可复盘？

**标准答案**：为每个关键事件记录发生时间、观察时间、Trace/Span 关联、资源、变更 ID、策略版本、操作者、结果和证据位置；原始输入、执行输出、人工修改和最终采用版本分开保存。恢复结束后形成时间线和差异清单，而不是只保留一条“成功”日志。

**深入思考**：
- **边界情况**：异步采集、时钟偏差和重复投递会打乱日志顺序；应区分事件发生的 Timestamp 与采集系统的 ObservedTimestamp，并用关联 ID 重建因果链。
- **源码层面**：稳定的 EventName 和低基数属性便于聚合，详细内容放入受控 Body/证据存储；敏感输入脱敏、限采和设置留存期限。
- **生产经验**：审计证据应能回答“谁在何时以什么授权对哪个对象做了什么，验收依据是什么”；来源证明只能说明制品如何构建，仍需结合运行时行为和业务验收。

## 0x16 2026-07-28：生产变更的可观测证据与可逆恢复

### 1. TypeScript /  发生版本、配置或数据结构变更时，如何证明兼容而不只是“能启动”？

**标准答案**：把协议、数据、配置、运行时和运维兼容性拆开，为每类建立旧版本基线、代表性流量和失败样本；通过双读/双写、灰度或金丝雀逐步放量，用成功率、错误率、P95/P99、资源消耗和恢复时间设定停止与回滚门槛。启动成功只证明进程存活，不能证明语义、顺序、幂等和故障恢复正确。

**深入思考**：不可逆迁移、缓存预热、消息重放和跨版本滚动升级必须单独演练；应用回滚不等于数据回滚，构建产物、配置快照、依赖清单和样本哈希要能支撑故障归因。

### 2. 如何把日志、指标和 Trace 组织成 TypeScript /  的可排障证据链？

**标准答案**：统一 service、environment、version、instance、request/message 等字段，在跨进程边界传播 Trace Context；指标负责趋势与告警，日志保留关键上下文，Trace 串起跨组件因果路径，并对敏感内容脱敏、采样和限期留存。

**深入思考**：异步队列、批处理、重试和线程池会打断直觉上的父子关系，应额外记录 producer、consumer、attempt 和业务关联 ID；排障演练应从用户症状跳到 Trace、日志、变更记录和恢复动作。

### 3. 性能优化或安全加固后，如何证明没有引入新的生产风险？

**标准答案**：保存变更前基线，用代表性负载和故障注入对比吞吐、P50/P95/P99、错误率、资源消耗、权限拒绝和恢复时间；再用小流量、自动回归、依赖扫描和发布门禁验证真实流量，明确测量误差与未覆盖风险。

**深入思考**：平均值会掩盖长尾；涉及 Agent、插件或外部输入时，还要验证提示注入、越权调用、敏感数据外泄和审计完整性。发布、暂停、回滚、数据补偿分别定义负责人和验收信号。


## 0x17 2026-07-29：变更契约、供应链证据与最小权限

### 1. 面对 TypeScript 的一次兼容升级，怎样把“能回滚”变成可验证的变更契约？

**标准答案**：先定义不变量、兼容窗口和停止条件，再把它们写成自动化检查：接口/Schema 的向后兼容测试、旧客户端与新服务的双向回放、关键 SLI/SLO 的分版本对比，以及明确的回滚入口。发布按小流量、短时段推进；只有当错误率、延迟、业务成功率和数据一致性均满足阈值，才扩大范围。回滚对象必须是可定位的版本或配置快照，不能依赖“临时再修一个补丁”。

**深入思考**：
- **边界情况**：数据库迁移、消息格式和缓存格式一旦不可逆，代码回滚也可能无法恢复；应采用 expand-contract、双写校验和延迟删除。
- **证据链**：记录变更 ID、构建产物、配置差异、受影响流量、指标窗口和审批人，复盘时才能区分代码、配置与外部依赖。
- **生产经验**：先演练停止发布和回滚，再上线；Google SRE 明确建议渐进发布、快速检测和安全回滚。

### 2. 如何证明部署的产物确实来自经过审查的源码，而不是“构建机里恰好生成的文件”？

**标准答案**：让构建过程产生可验证的 provenance：绑定仓库、提交 SHA、工作流、环境和触发事件，必要时同时生成 SBOM；部署侧按组织策略验证签名/证明、来源和允许的构建环境，再允许进入高风险环境。证明“从哪里来”不等于证明“绝对安全”，仍要结合依赖审计、测试和人工风险判断。

**深入思考**：
- **对比延伸**：哈希只能证明内容一致，签名/attestation 才能把内容与来源、构建步骤关联起来；两者应一起使用。
- **回滚关系**：保留可验证的上一版产物和声明，回滚时验证旧产物，而不是重新构建一个“看起来一样”的版本。
- **官方依据**：GitHub 文档说明 Artifact Attestations 用于建立构建来源，并支持用 CLI 验证二进制、容器和 SBOM 证明。

### 3. 在 TypeScript 系统接入自动化 Agent 或高权限工具时，如何避免“模型说错一句话就造成生产事故”？

**标准答案**：把授权放在模型之外：工具按最小功能拆分，使用调用者上下文和最小权限，服务端对参数、资源范围、速率和状态再次校验；删除、发布、转账、权限变更等高影响动作必须人工确认。所有调用记录 trace、输入摘要、工具参数、结果、拒绝原因和审批信息，并配置熔断、限流与可逆操作。

**深入思考**：
- **安全边界**：不能把“请模型自我约束”当作授权机制；间接提示注入、恶意工具结果和被污染的上下文都可能改变模型决策。
- **可观测性**：异常不应只看最终回答，还要关联模型调用、工具调用、下游写入和人工接管，才能定位越权链路。
- **官方依据**：OWASP 将过度功能、过度权限和过度自主列为 Excessive Agency 的根因，并建议最小化扩展、下游强制授权和高影响动作人工批准。

## 0x18 2026-07-31：变更后验证、故障注入与策略回退

### 1. TypeScript 的变更已经上线后，如何证明它真的改善了用户结果？

**标准答案**：先定义用户可感知的 SLI/SLO 与变更前基线，再用小流量或分阶段发布比较成功率、错误预算消耗、P95/P99、资源成本和业务完成率；把观测窗口、停止阈值、样本范围和回滚动作写入发布契约。不能用“进程存活”或单一平均值代替用户结果。

**深入思考**：短期指标变好可能掩盖长尾、重试放大、异步积压或低频高影响错误；验证应覆盖峰值、依赖异常、数据回放和恢复后的完整性。若结论不适用于某类租户、地区或流量，应明确标注，而不是泛化为全量安全。

### 2. 如何设计故障注入，既能暴露真实问题，又不会把生产变成实验场？

**标准答案**：从风险模型和历史事故选择最小故障单元，先在隔离环境与影子流量中验证，再以受控范围、可观测停止条件和明确负责人推进；注入网络超时、依赖拒绝、资源耗尽、消息重复或权限拒绝，并检查告警、降级、幂等、人工接管和恢复后的数据一致性。

**深入思考**：故障注入的成功标准不是“系统没挂”，而是能在预期时间内发现、隔离、恢复并留下证据。对不可逆写入、支付、删除和权限变更等动作，应优先使用模拟器、沙箱或只读替身，避免用真实副作用换取测试覆盖率。

### 3. 当错误预算或安全门禁被触发时，如何决定暂停、降级、回滚还是继续发布？

**标准答案**：把动作绑定到事先约定的阈值和证据：错误预算燃烧、关键 SLI、影响范围、变更可定位性、依赖健康度、权限拒绝率和恢复时间共同决定策略。达到高风险阈值就停止扩散并保留上一版可验证产物；只有根因明确、修复经过回归且观测恢复，才逐步解除限制。

**深入思考**：回滚不是万能的，数据迁移、缓存格式、消息协议和外部副作用可能不可逆；需要同时准备前向修复、补偿任务、凭据轮换和审计留痕。对 Agent 或自动化工具，授权层必须独立于模型，并对高影响动作要求人工批准。

## 0x19 2026-08-03：变更契约、语义观测与可验证回退

### 1. 如何把一次生产变更写成可执行的变更契约？

**标准答案**：在发布前明确变更范围、兼容性假设、成功指标、停止阈值、观测窗口、负责人和回退动作；把代码、配置、数据库/消息协议、依赖版本与构建产物摘要绑定起来。发布后按小流量或分阶段验证，不能只以进程存活判断成功。

**深入思考**：契约的价值在于让“继续、暂停、降级、回滚”成为证据驱动的决策。数据迁移和外部副作用可能不可逆，因此要同时准备前向修复、补偿任务、幂等重放与审计记录。

### 2. 观测系统如何记录变更过程中的关键状态，而不是堆日志？

**标准答案**：持续操作用 span，瞬时的发布、配置切换、人工批准、熔断和回滚用带时间戳的结构化 event；为事件定义稳定名称、低基数属性、严重级别和关联 trace，并把版本、租户/分区、结果和拒绝原因纳入查询维度。

**深入思考**：日志内容不等于证据链。需要把请求、依赖调用、重试、异步消息、下游写入和人工接管串联起来，同时对凭据、个人数据和高基数输入脱敏、限采和设定留存期。

### 3. 如何证明回滚的确是“上一版”，而不是重新构建的相似产物？

**标准答案**：为构建产物和 SBOM 记录 provenance/attestation，绑定仓库、提交、工作流、环境和摘要；发布门禁验证签名、主体摘要和允许来源，回滚时直接选择已验证的上一版产物，并保留审批与执行证据。

**深入思考**：attestation 证明来源和构建过程，不等于软件绝对安全；仍需结合测试、依赖审计、授权策略和业务风险判断。对 Agent 或自动化工具，还要把模型、提示模板、工具适配器和权限策略纳入版本闭环。

## 0x1A 2026-08-04：恢复演练、数据校验与人工接管

### 1. 变更产生副作用后，如何设计可恢复流程？

**标准答案**：把规划、执行、提交拆开；高风险动作先生成待确认计划，执行时记录请求、工具版本、输入摘要、结果和操作者；写入外部系统时使用幂等键、事务边界或补偿动作，并保留可验证的撤销路径。回退不能只看服务是否恢复，还要核对数据、权限和对外通知是否恢复到一致状态。

**深入思考**：恢复动作本身也可能失败，因此要有停止条件、人工接管和只读核查模式。发布流程可用小范围、限时的 canary 降低影响；观测字段应采用稳定语义约定，便于跨组件比较。

### 2. 如何判断系统的“成功”而不是只看 HTTP 200？

**标准答案**：为任务定义业务验收条件，例如目标记录存在且字段满足不变量、外部副作用只发生一次、敏感数据没有越权流出；同时记录 trace、重试、拒绝和人工修改等事件。把自动评估、抽样人工复核和回放测试结合起来，失败时保留可重现证据。

**深入思考**：响应正确不代表状态正确；评估集还要覆盖超时、重复消息、部分成功和依赖返回异常。指标应区分组件质量、依赖可靠性和业务结果，避免把某一层的退化掩盖掉。

### 3. 什么时候必须把决策交给人？

**标准答案**：涉及付款、删除、权限授予、医疗法律结论、对外发布或不可逆数据变更时，默认采用人审或双人确认；自动化系统只能准备证据、说明影响范围和给出候选动作。人工界面要展示原始来源、差异、风险、授权范围与撤销方式，并记录最终决定。

**深入思考**：人工接管不应只由“系统不确定”触发，还应由风险等级、异常次数、预算、权限边界和证据缺失触发。参考：[Google SRE Canarying Releases](https://sre.google/workbook/canarying-releases/)、[OpenTelemetry Semantic Conventions](https://opentelemetry.io/docs/specs/semconv/)、[OWASP Securing Agentic Applications Guide](https://genai.owasp.org/resource/securing-agentic-applications-guide-1-0/)。

## 0x1B 2026-08-05：变更影响边界、故障注入验收与人工接管（TypeScript）

### 1. 如何把一次 TypeScript 变更定义成可验证的影响边界，而不是只看代码 diff？

**标准答案**：先写变更契约：输入/输出、兼容窗口、数据与权限边界、受影响依赖、成功指标、停止条件和回退对象；再把契约映射到小流量或隔离环境，按 canary 与 control 对比错误率、延迟、正确性和资源信号。只要无法回答“谁受影响、何时停止、回到哪个已知版本”，就不应直接全量发布。

**深入思考**：边界不能只按服务名划分，还要覆盖配置、依赖版本、缓存、消息积压和异步作业。共享数据库或跨阶段流水线会污染对照组，应按工作单元保持同一版本池，并把业务正确性纳入验收；Google SRE 也强调可归因指标、分阶段 canary 和可回退的小变更。

### 2. 如何用故障注入证明 TypeScript 变更的回退和恢复真的可用？

**标准答案**：在影子流量或隔离租户中注入超时、依赖错误、重复消息、部分写入和权限拒绝，验证告警、自动暂停、人工升级、回退执行及回退后的数据一致性。验收证据至少包括变更版本、输入摘要、trace、停止原因、恢复动作、业务核对结果和未完成任务清单。

**深入思考**：服务恢复不等于业务恢复；数据库迁移、外部副作用和已发送通知可能不可逆，不能用“重新部署旧包”掩盖补偿需求。故障演练要设明确的退出条件和最大影响面，回退失败时转入只读、限流、降级或人工接管，并保留可审计证据。

### 3. 高风险操作何时必须交给人工，如何避免“人工接管”变成口头流程？

**标准答案**：删除、付款、授权、对外发布、跨租户访问和不可逆数据修改等动作应设置策略门禁：最小权限、短期凭证、双人确认、幂等键、撤销/补偿路径和超时升级。Agent 或自动化系统只能提出计划与证据，不能以模型置信度代替授权；人工确认结果要写回审计链并能关联到最终业务状态。

**深入思考**：人工接管不是暂停按钮，而是一个可演练的状态机：谁接手、接收哪些上下文、允许哪些动作、何时恢复自动化、怎样复盘。对 TypeScript 的生产流程，至少准备“继续、暂停、回退、降级、终止”五种明确分支。

## 0x1C 2026-08-18：可回退发布、证据化观测与供应链验证（TypeScript）

### 1. 在 TypeScript 中，如何设计真正可回退的生产发布？

**标准答案**：先把发布对象、兼容窗口、影响范围、成功指标、停止阈值、责任人和回退目标写成变更契约；构建阶段固定提交、依赖解析结果和产物摘要，发布阶段采用小流量或分阶段策略，并让路由、配置和数据变更具备明确的反向动作。回退时直接选择已验证的旧产物，不临时重建“看起来相同”的版本；对数据库、消息、缓存和外部副作用分别准备兼容策略、幂等处理或补偿流程。

**深入思考**：
- **边界情况**：代码可以回退，但已执行的 schema 迁移、已发送消息和外部写入可能不可逆，因此要区分版本回退、流量切换、前向修复和业务补偿。
- **源码层面**：把发布控制面、数据面和异步消费者的版本选择记录在同一变更 ID 下，检查重试、超时和部分成功路径，避免只有 HTTP 服务回退而后台任务仍运行新逻辑。
- **生产经验**：先在隔离租户、影子流量或低风险分区演练停止和恢复；回退成功的判据应包含业务不变量、积压、权限和外部通知，而不是只看进程重新变为健康。

### 2. 如何把 TypeScript 的发布结果做成证据化观测，而不是只看成功率？

**标准答案**：用指标观察总体趋势，用 trace 关联请求、依赖、重试和异步任务，用结构化事件记录发布开始、配置生效、人工批准、停止、降级和回退，用日志保存必要的上下文与错误样本。每条证据绑定变更 ID、版本/产物摘要、环境、分区、结果和时间窗口；同时对凭据、个人数据、提示词和高基数输入脱敏、限采并设定留存期限。

**深入思考**：
- **边界情况**：低错误率也可能掩盖业务结果错误、单一租户受损、重试风暴或延迟尾部退化，所以必须把业务验收和 control/canary 对照纳入停止条件。
- **源码层面**：统一事件名称和属性，确保入口 span、下游调用、消息消费、数据库写入和人工接管能在同一 trace 或关联 ID 下检索；不要把一整段输入直接塞进 span 属性。
- **生产经验**：先定义“继续、暂停、降级、回退、人工接管”的证据阈值，再配置告警；观测系统自身故障时，应保留最小审计事件和安全默认值，不能因指标缺失而自动全量放行。

### 3. 如何验证 TypeScript 的依赖与构建产物，避免回滚到来源不明的版本？

**标准答案**：锁定依赖解析结果并保存校验和，生成 SBOM 和构建 provenance/attestation，将仓库、提交、工作流、构建环境、产物摘要和策略版本关联起来。发布门禁验证签名、主体、摘要、允许的来源和漏洞/许可证策略；部署与回退都只接受通过门禁的不可变产物，并把例外审批、时限和后续补救写入审计链。

**深入思考**：
- **边界情况**：attestation 能证明来源与构建过程，但不能证明代码绝对无漏洞；仍需结合测试、依赖审计、运行时权限和业务风险判断。
- **对比延伸**：源码仓库保护、锁文件校验、镜像签名、SBOM 和 provenance 解决的是不同问题，不能用其中一个替代全部供应链控制；最小可行门禁也要覆盖 transitive dependency 和构建脚本。
- **生产经验**：紧急回退允许临时例外时，必须限定产物摘要、操作者、环境和过期时间；若无法验证来源，应选择已知安全版本或降级到只读/限流模式，而不是绕过验证。
