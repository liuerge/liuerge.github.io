0x00-02. React 18 的并发特性有哪些？

特性 API 说明
Automatic Batching 默认开启 setState 自动合并渲染
Transitions useTransition / startTransition 标记低优先级更新
Suspense <Suspense> 数据加载的声明式 fallback
useDeferredValue useDeferredValue(value) 延迟更新某值

深入思考：

  • 机制层面：并发特性的本质是渲染过程可中断、可恢复——Fiber 让 React 在一个时间切片用完后让出主线程，被中断的是尚未提交的低优先级渲染，已提交的 DOM 不会被回滚。startTransition 标记的更新仍会照常执行，只是可被输入、点击这类紧急更新插队。
  • 边界情况：Transition 只降低调度优先级，不会减少渲染次数，也不会让渲染中的副作用变得安全——过渡内的组件仍必须是纯函数，不能依赖“这次渲染什么时候被执行”。
  • 对比延伸：useTransition 返回 isPending 供你显式控制加载态，useDeferredValue 则只交出延迟后的值，适合拿不到 setter 或不想改造更新路径的场景；前者管“这组更新”，后者管“这个值”。
  • 生产经验：过渡适合输入联想、Tab 切换、图表重算等可等待的更新；如果把用户需要即时看到的回显也放进 Transition，典型表现是输入变卡，比不用并发特性还糟。

0x01 Hooks 原理

0x01-01. useState 和 useEffect 的底层实现？

标准答案：React 用 Fiber 节点上的链表保存 Hooks 状态：每个函数组件对应一个 Fiber，其 memoizedState 指向第一个 Hook 节点，节点之间通过 next 串成单向链表，节点里保存当前状态值以及该状态的更新队列。useState 返回的就是节点上的状态，setState 把更新挂进该节点自己的队列并调度一次重新渲染；useEffect 同样占用一个节点，在 commit 阶段根据依赖数组决定是否执行，并把 effect 与清理函数记录在节点上。渲染时 React 按调用顺序依次读取链表，所以 Hooks 的数量和顺序在每次渲染中必须完全一致，这正是 Hooks 不能写在条件、循环或提前 return 之后的原因。简化的讲解常用数组加下标模拟这套机制，但真实实现是链表加更新队列，这也是同一组件内多次 setState 能被按顺序合并处理的基础。

Hooks 基于 Fiber 节点的链表存储：

为什么 Hooks 不能放在条件语句里？
因为 Hooks 靠调用顺序索引。如果某次渲染跳过一个 Hook，所有后续 Hook 的索引都会错位，导致状态混乱。

深入思考：

  • 机制层面：每个 Hook 在 Fiber 上是一个 { memoizedState, queue, next } 节点，按调用顺序串成单向链表。useState 的当前值存在节点上，setState 把更新挂进该节点自己的队列并调度重新渲染，下次渲染按顺序取出并消费队列。
  • 边界情况：正因为靠顺序索引，Hooks 不能出现在条件、循环或提前 return 之后；useEffect 的清理函数也按顺序与上一次的 effect 一一对应，漏掉或跳过任何一个 Hook 都会让后续 Hook 全部错位，报错信息通常指向“渲染的 Hook 比上次多/少”。
  • 对比延伸：useState 是排队加批处理，多次调用会顺序消费并支持函数式合并；useEffect 的时机由 commit 阶段决定，被动 effect 在绘制后异步执行，useLayoutEffect 则在浏览器绘制前同步执行，用于读取布局。
  • 生产经验：effect 里读到旧值基本是依赖数组不完整导致的闭包问题，与其把整个对象塞进依赖数组，不如用 ref 保存最新回调、用函数式更新读取最新状态，避免 effect 反复重建又读到过期值。

0x01-02. useMemo、useCallback、React.memo 什么时候用？

标准答案：三者的优化对象并不相同。useMemo 缓存计算结果，只有依赖变化时才重新计算，用于计算昂贵或需要稳定引用的值；useCallback 缓存函数引用，让依赖它的子组件或 effect 不会因为函数每次重建而失效；React.memo 包裹组件，在 props 浅比较相等时跳过该组件的重新渲染。它们本身都有比较依赖、保存缓存的开销，对简单计算或几乎总是变化的 props 使用反而更慢，所以判断顺序应该是先确认存在性能问题，再针对“重计算”“引用不稳定”“频繁重渲染”中的具体一类选择对应 API。文章给出的原则是能不用就不用，只在有明确收益的边界上使用。

不滥用原则：只在确实有性能问题时才用。useMemo 本身有开销（比较依赖数组），对简单计算反而更慢。

深入思考：

  • 传给子组件的回调函数 → 必须用 useCallback，否则子组件的 React.memo 形同虚设（每次父组件渲染都会生成新函数引用）

0x02 状态管理

0x02-01. Context 和状态管理库（Zustand/Jotai）怎么选？

方案 适用场景 缺点
useState 组件内部状态 跨组件共享需 prop drilling
Context 主题/语言/认证等全局低频变更 任何 Context 值变化，所有消费者重渲染
Zustand 中大型应用全局状态 需要理解 selector 机制
Jotai 原子化状态，细粒度更新 原子多了难管理

Context 优化：拆分 Context 或使用 useMemo 包裹 value，避免不必要的重渲染。

深入思考：

  • 机制层面：Context 解决的是跨层级传递，不解决订阅粒度——Provider 的 value 引用变化后所有 useContext 消费者都会重渲染。Zustand 用外置 store 加 selector 订阅，只有 selector 返回值变化才通知对应组件，所以天然做到了按字段订阅。
  • 边界情况：如果放进 Context 的是高频变化的数据（行情、拖拽坐标、鼠标位置），即便拆成多个 Context 也挡不住大范围重渲染，这类数据更适合外置 store、ref 加订阅，或直接绕过 React 渲染更新 DOM。
  • 对比延伸：Zustand 偏集中式，一个 store 配多个 selector，适合中大型应用的全局状态与派生计算；Jotai 偏原子化，组件只订阅自己依赖的原子，适合更新范围小但依赖关系复杂的细粒度场景。
  • 生产经验：主题、语言、登录用户这类低频读多写少的配置用 Context 足够；只有当出现服务端缓存、复杂派生和跨模块同步时再引入状态库，否则两套机制并存会让数据来源变得难以追踪。

0x03 性能优化

0x03-01. React 性能优化的系统方法

标准答案：React 性能优化应该按“定位、减少渲染、减少计算、减少 DOM”的顺序推进，而不是先堆优化 API。第一步用 Profiler 的 actualDuration 与 baseDuration 找出真正耗时的组件和渲染次数；第二步用稳定的 key、组件拆分和状态下沉减少不必要的重渲染；第三步用 useMemo/useCallback/React.memo 处理重计算与引用不稳定；第四步用虚拟列表、懒加载和代码分割控制 DOM 数量与首屏体积。每一步都要有量化指标（渲染耗时、渲染次数、chunk 大小、LCP/CLS）验证收益，避免为了“看起来优化”而增加复杂度。只有定位到具体瓶颈后再引入对应手段，否则优化本身会成为新的维护成本。

深入思考：

  • 机制层面：优化顺序应当是先定位、再减少工作量、最后减少渲染次数。用 Profiler 的 actualDuration 与 baseDuration 找出真正耗时的子树，再判断瓶颈是计算重、渲染次数多，还是 DOM 节点数量大，避免凭直觉加 memo。
  • 边界情况：memo 只在 props 浅比较相等时跳过渲染，父组件每次传新对象或新函数时它完全不生效；用数组下标作为 key，在插入删除时会触发错误的节点复用，性能问题会伪装成状态错乱。
  • 对比延伸：长列表的瓶颈在 DOM 数量，虚拟化收益远大于 memo；重计算瓶颈在 CPU，useMemo 才有意义；两者不能互相替代，先分清瓶颈类型再选手段。
  • 生产经验：debounce/throttle 这类需要稳定引用的工具函数放进 useMemo 初始化，否则每次渲染都会新建定时器；同时记得在卸载时清理，避免组件已卸载仍在触发更新。

0x04 SSR / Next.js

0x04-01. SSR 和 CSR 的区别？Next.js 的渲染策略？

策略 首屏速度 SEO 交互复杂度
SSR 快 ✅ 中等
SSG 最快 ✅ 纯静态
ISR 快（缓存后） ✅ 定时更新
CSR 慢 ❌ 高交互

水合 (Hydration)：SSR 发送 HTML → 客户端加载 JS → React 把事件绑定到已有的 DOM 上。如果服务端和客户端渲染不一致，会报 Hydration mismatch。

深入思考：

  • 机制层面：SSR 在服务端执行一次组件渲染生成 HTML，客户端再加载同一份组件代码做 hydration，把事件与状态挂到已有 DOM 上；CSR 只有空壳 HTML，首屏要等 JS 下载、执行、请求数据三步走完，所以首字节快但内容出现晚。
  • 边界情况：hydration 只负责附加交互，不会重跑服务端已完成的 DOM 构建；只要服务端与客户端首次渲染结果不一致（时间、随机数、window、浏览器扩展改 DOM），就会触发 mismatch 并让该子树回退为客户端渲染。
  • 对比延伸：SSG 在构建时生成，ISR 在运行期按 revalidate 重新生成，SSR 每次请求生成；Streaming 把一次渲染拆成多个 chunk 沿 Suspense 边界逐步发出，让慢数据不阻塞已就绪部分。
  • 生产经验：营销页、文档站优先 SSG/ISR，登录后的强实时页面用 SSR 或 RSC；判断标准是“这份内容对多少用户是同一份”，把同一份内容放在每个请求里重复渲染是最常见的浪费。

0x05 React 19 新特性与生产实践

0x05-01. React 19 use() Hook 深度解析——在渲染中直接消费 Promise

难度：⭐⭐⭐⭐（专家）

问题：React 19 引入的 use() Hook 允许在渲染过程中直接消费 Promise，它如何改变了 React 的异步数据处理模式？

核心原理：

use() vs useEffect 数据获取对比：

维度 useEffect + useState（旧模式） use() + Suspense（React 19）
代码行数 ~15 行（loading/success/error） ~5 行
渲染次数 3 次（mount → loading → data） 2 次（fallback → data）
竞态条件 需手动取消 AbortController 自动处理
错误处理 try/catch in useEffect <ErrorBoundary>
SSR 支持 需手动处理 原生支持
状态管理 需 useReducer/第三方 React 内置

🔥 踩坑案例：Server Action + use() 在 Client Component 中的错误用法（某电商团队）

  • 场景：使用 React 19 Server Actions + use() 实现表单查询
  • 问题：在 Client Component 中直接调用 Server Action 时，use() 报错
  • 修复：use() 在 Client Components 中是实验性的（Stable in Server Components only），需要包裹在 <Suspense> 中并配合 Server Component 使用

面试金句：

“React 19 的 use() 把数据获取从 useEffect 的世界拉到声明式渲染中。不必再手动管理 loading/error/竞态。但记住——use() 在 Server Components 中完全稳定，在 Client Components 中仍是实验性功能。”

深入思考：

  • 机制层面：use(promise) 在渲染阶段读取 Promise 状态，未完成时把该渲染挂起到最近的 Suspense 边界并注册回调，Promise 完成后 React 重新渲染这个组件；它不是 await，而是渲染被打断并在数据就绪后重试。
  • 边界情况：Promise 必须是稳定引用。若在渲染函数里直接 use(fetch(...))，每次渲染都会产生新 Promise，形成无限挂起和重复请求；文章中那个 Server Action 的误区，本质也是 Promise 的来源与渲染边界不匹配。
  • 对比延伸：useEffect + useState 是“先渲染空态、再拉数据、再触发一次渲染”，至少多一轮且要手写竞态取消；use() 把加载态交给 Suspense、把错误交给 ErrorBoundary，但它不负责缓存与请求去重，仍需数据层配合。
  • 生产经验：把 Promise 的创建与消费分离——在服务端组件或带缓存的函数里创建并缓存，在需要数据的地方 use() 消费；在 Client Component 中使用前先确认当前框架对该能力的支持程度，不要把实验性路径当稳定 API 用。

“React Server Components 的生产最佳实践可以总结为一句话：Server 负责数据，Client 负责交互。'use client' 关键字用在你需要 useState/useEffect/onClick 的地方，否则默认都是 Server Component。最大的坑是 Client Component 不能直接 Import Server Component——要用 children 传递。”

深入思考：

  • 机制层面：RSC 的收益来自组件树在服务端渲染并序列化为 Payload，客户端只下载需要交互那部分组件的 JS。因此最优结构是让数据获取与静态展示留在 Server Component，把 'use client' 下沉到真正有状态或事件的叶子组件。
  • 边界情况：Client Component 不能直接 import Server Component，但可以通过 children 或 props 接收父级 Server Component 传入的已渲染内容；一旦在 'use client' 文件顶层引入服务端专属模块，整棵子树都会被拉进客户端 bundle。
  • 对比延伸：RSC 减少的是 bundle 体积和服务端到客户端的冗余数据，Suspense 解决的是流式与加载态，两者常配合但职责不同；把 RSC 当成性能开关而不区分数据边界，往往只得到更大的 Payload 和更长的首屏等待。
  • 生产经验：重构时先画出“数据在哪获取、交互在哪发生”两条边界，再用 children 模式隔离图表、编辑器这类必须客户端的重型组件；同时监控 Payload 体积，服务端渲染过多重复 JSON 会抵消 RSC 的收益。

1. forwardRef 废弃警告

1. RSC Payload：不是 HTML，而是序列化的 React 元素树——一个 JSON 数组，包含组件类型、props 和引用：

2. Streaming：Server Component 可以按 Suspense 边界分段流式传输：

面试金句：RSC 的本质不是”服务端渲染”，而是”服务端渲染组件树并序列化为客户端可以消费的协议格式”。Server Actions 提供了从客户端触发服务端数据变更的能力，两者结合构成了”后端驱动前端”的全栈范式。

参考：RSC 官方文档

深入思考：

  • 机制层面：RSC 传输的是序列化的组件树描述而非 HTML 字符串，客户端据此重建虚拟树；Suspense 边界是流式发送的最小单位，服务端可以在慢数据就绪前先把外壳和已完成边界 flush 出去。
  • 边界情况：Server Action 本质是 POST 端点，执行完通过 revalidatePath/revalidateTag 触发相关 Server Component 重新渲染并回推新的 Payload，客户端就地更新；Action 的返回值同样受序列化约束，不能返回函数或类实例。
  • 对比延伸：传统 SSR 要把整页组件代码交给客户端水合，RSC 让服务端组件完全没有客户端 JS；Server Actions 与 REST/GraphQL 的区别在于它把“数据变更 + 重新渲染”合并成一次往返，省掉客户端手动刷新缓存的逻辑。
  • 生产经验：把 Suspense 边界放在慢且独立的数据块上，例如导航先出、图表后到；边界过粗会让整页等待最慢的请求，边界过细则会产生大量零碎 chunk 与界面抖动。

0x06-03. RSC 与传统 SSR 的核心区别是什么？为什么说 RSC 不是 SSR 的替代？

标准答案：

维度 传统 SSR (React 18-) RSC (React 19+)
输出格式 HTML 字符串 RSC Payload（序列化 VDOM）+ HTML 流
组件是否发送到客户端 所有组件的 JS bundle 都发送 Server Component 的 JS 零发送
数据获取方式 getServerSideProps 或手动注水 组件内部直接 async/await 或 use()
交互性（水合） 必须水合整个页面 只需水合 Client Component 部分
流式传输 可选的（renderToPipeableStream） 默认流式，按 Suspense 边界
缓存粒度 页面级（ISR） 组件级 + 数据级
状态保持 页面间导航丢失滚动/输入状态 RSC Payload 保持 Client 状态
适用场景 内容型网站，需要完整 HTML 混合型应用，部分交互+部分服务端

为什么 RSC 不是替代 SSR 的？

RSC 和 SSR 解决不同维度的问题：

  • SSR（Server-Side Rendering）：解决的是”首屏怎么更快”——把 JS 生成 HTML，让用户更早看到内容
  • RSC（React Server Components）：解决的是”哪些代码不需要发到客户端”——让服务端组件不贡献 JS bundle 大小

深入思考：

  • Bundle 节省：一个 Server Component 若用 moment.js 做日期格式化，传统 SSR 会把 moment.js 整个发送到客户端；RSC 下 moment.js 只存在于服务端
  • 交互性差距：传统 SSR 必须等待完整水合才能交互；RSC + Streaming 让可交互部分（Client Components）优先水合

参考：RSC vs SSR 深度解析

0x06-04. RSC 的序列化限制是什么？哪些东西不能从 Server Component 传到 Client Component？

标准答案：

Server Component 渲染的结果会序列化为 RSC Payload（JSON-like 格式）发往客户端，因此只有可序列化的值才能作为 Server Component 的 props 传递给 Client Component：

不能传递的类型：

类型 原因 示例
函数 JSON 无法表示函数 function() {}、() => {}、方法
Date 对象 序列化为字符串而非 Date new Date() → 客户端拿到的是字符串
Class 实例 原型链丢失 new MyClass()
Map / Set 非 JSON 原生类型 new Map()、new Set()
Symbol JSON 不支持 Symbol('id')
undefined JSON.stringify 会移除 通常变为缺失字段
循环引用对象 JSON.stringify 会报错 const a = {}; a.self = a;
React Element 除非用 cloneElement 特殊处理 <div /> 不能直接传递
Request/Response 浏览器 API，不可序列化 只在 HTTP 层有效

特殊处理技巧：

  • Date 对象：传 date.toISOString()，在 Client Component 中 new Date(isoString)
  • 需要回调的场景：Server Component 不能传递 onclick 给 Client Component——交互必须封装在 Client Component 内部
  • 类实例：拆解为普通对象传输，Client 侧重新实例化

面试金句：RSC 的序列化限制本质上是”服务端和客户端之间的网络边界”。一旦你接受了这个限制，模式就很清晰了——Server 负责数据准备，Client 负责交互行为。

参考：RSC 序列化规则

深入思考：

  • 机制层面：RSC Payload 是跨网络的类 JSON 协议，只能承载 JSON 可表达的值，再加上 React 约定的特殊标记（元素、Client Component 引用、Promise 等）。Date、Map、Set、类实例会在这一步退化为普通对象或字符串，原型信息随之丢失。
  • 边界情况：函数和事件处理器不能从 Server Component 传给 Client Component，因为交互必须发生在有客户端 JS 的一侧；需要回调时应在 Client Component 内部定义，而不是试图让闭包穿过这条网络边界。
  • 对比延伸：这与传统 SSR 的 props 不经过序列化、在同一进程内直接渲染不同——RSC 引入了真正的进程与网络边界，所以限制更接近 RPC 的入参约束，而不是普通组件传参。
  • 生产经验：跨边界前统一转换为可序列化的 DTO（时间戳、纯对象数组），客户端按需重建类型；对第三方库返回的类实例要显式转换，否则线上表现为字段都在、方法调用却报错。

0x06-05. Server Actions 的安全注意事项——资深研发必知

标准答案：

每个 'use server' 函数本质上是一个公开的 HTTP POST 端点——不论你写多少 TypeScript 类型和前端校验，攻击者可以用 curl 直接调用。必须把 Server Action 当作 API 来防护：

五大安全陷阱：

1. 输入校验缺失

2. 认证检查缺失

3. 授权（Authorization）遗漏

  • 认证 ≠ 授权——用户已登录不代表他能删除别人的数据

4. CSRF 误解

  • Next.js Server Actions 有内置的 Origin 头校验，提供基础的 CSRF 防护
  • 但 API Routes 没有！如果 Server Action 调用了内部的 API Route，需要额外防护

5. 速率限制缺失

  • Server Action 可被无限调用 → 可能造成 DoS 或高额账单

面试金句：Server Actions 的便利性是一把双刃剑——它消除了 API 层的样板代码，但也意味着你需要在前端代码中嵌入服务端安全逻辑。规则很简单：对每一个 'use server' 函数，问自己——如果这是一个公开的 POST 端点，我该怎么做安全防护？

参考：Secure Next.js Server Actions

深入思考：

  • 机制层面：每个 'use server' 函数都会被编译成一个可被外部直接调用的端点，TypeScript 类型在运行时并不存在，前端校验也可被绕过，所以输入校验、认证、授权、限流必须在服务端 Action 内各自独立完成。
  • 边界情况：认证回答“你是谁”，授权回答“你能不能操作这条数据”；只判断登录状态而不把所有者或租户条件写进数据库查询，会导致水平越权，这是这类端点最常见的漏洞形态。
  • 对比延伸：框架为 Server Action 提供了内置的 Origin 校验来降低 CSRF 风险，但普通 API Route 没有；当 Action 内部再调用 API Route 时，这层防护不会自动传递，需要单独处理。
  • 生产经验：把每个 Action 当作公开写接口设计——入参用运行时 schema 校验、按用户与 IP 限流、数据库层带权限条件、失败信息不回显内部细节，同时在网关记录调用量以便发现异常批量调用。

深入思考：

  • 机制层面：括号目录只参与代码组织和布局嵌套、不进入 URL；@slot 目录把同一 URL 拆成多个可独立渲染的命名区域，由布局决定摆放位置；拦截路由用 (.)/(..) 表示相对层级，让同一条 URL 在客户端导航进入时匹配到模态实现。
  • 边界情况：平行路由需要为每个 slot 提供兜底页面，否则硬刷新或从其他路由返回时该 slot 无内容会导致整页 404；拦截路由只在客户端导航时生效，直接输入地址或刷新会落到真实页面，设计时要保证两种呈现共享同一份数据。
  • 对比延伸：Route Groups 解决“同一 URL 空间要不同布局”，Parallel Routes 解决“同一页面要多个独立数据流与加载态”，Intercepting Routes 解决“同一内容两套呈现”，三者组合才能实现模态加深度链接的模式。
  • 生产经验：模态叠加拦截路由时，关闭动作应触发路由返回而不是仅隐藏 DOM，这样后退键行为一致、URL 始终可分享；同时为每个 slot 配好各自的 loading 与 error 边界，避免一个区域失败拖垮整页。

0x08-07. React 19.2 <Activity /> 组件——保留后台组件状态的革命性 API

难度：⭐⭐⭐⭐（专家）
问题：React 19.2 引入的 <Activity /> 组件解决了什么问题？与条件渲染有何不同？

标准答案：
React 19.2（2026 年 3 月）引入了 <Activity /> 组件——允许将渲染树标记为「非活动」（inactive），但不卸载其内容。传统条件渲染中，如果 {show && <Component />} 中的 show 变为 false，<Component /> 会被卸载，其内部状态（useState、useRef、useEffect）全部丢失。<Activity /> 提供中间状态：组件可见性由 Activity 控制，但组件树保持挂载，状态、ref、DOM 引用都保留。核心 API：<Activity mode="visible" | "hidden" | "inactive">——visible 正常渲染，hidden 隐藏但不卸载（类似 CSS visibility: hidden），inactive 完全非活跃（可能被 Suspense 暂停，但状态保留）。

深入思考：

  • 实现原理：<Activity /> 在 React Fiber 层面引入了新的 Offscreen 模式。Fiber 树在 inactive 模式下不会触发 useEffect cleanup，也不会调度提交阶段（Commit Phase）。DOM 节点会被移除（display: none 或从父容器分离），但 Fiber 引用保留。inactive 节点不会参与正常的渲染调度——在 Concurrent Mode 中，Activity 的子树的优先级被降为最低。
  • 与 KeepAlive 的区别：Vue 的 <KeepAlive> 和 React 的 <Activity> 目标相似但实现不同。KeepAlive 缓存整个组件树的 VNode（包括 DOM），而 Activity 在 Fiber 层面控制渲染，状态保留但不缓存 DOM（inactive 移出 DOM 树）。Activity 的内存占用小（只保留 Fiber 引用和状态），KeepAlive 保留完整 DOM。
  • 生产典型场景：Tab 切换（保留非活跃 Tab 的滚动位置和输入数据）、Modal 切换（隐藏一个 Modal 打开另一个，不丢失表单数据）、列表缓存（滚动到某一项时标记其他项为 inactive，保留它们的滚动监听和数据）。

生产踩坑：
某团队在 Dashboard 应用中使用了 <Activity mode="inactive"> 来缓存状态（4 个 Tab 页面，每个页面包含复杂的表格和图表）。上线后观察到页面切换时偶尔出现「白屏」——切换到某个 Tab 时内容空白，持续 2-3 秒后恢复。排查发现：<Activity mode="inactive"> 会将子树的调度优先级降到 Idle（最低优先级），当某个 Tab 中的组件包含 useDeferredValue 或 startTransition 时，这些极低优先级的任务被 React 的调度器无限推迟，导致内容渲染被完全阻塞。根因：Activity 的 inactive 模式将 Fiber 的 lane（优先级跑道）重置为 Idle，调度器在有空闲时才执行——但如果主线程一直被高优先级任务（如输入响应、动画帧）占用，Idle 任务永远不会被执行。修复：将有实时更新需求（如定时器、WebSocket 更新）的 Tab 改为 mode="hidden"（CSS 隐藏但渲染循环正常运行），只有纯静态内容的 Tab 才用 inactive。教训：<Activity mode="inactive"> 会完全暂停子树的渲染调度——如果子树中有需要持续更新的内容（如倒计时、数据轮询），inactive 会使其永远停止更新。mode="hidden" 保留了渲染循环但是视觉隐藏，更适合有实时更新的场景。

面试金句：

<Activity /> 是 React 在「状态保留」方面的原生解决方案——它解决了组件卸载导致状态丢失这一 React 长期存在的痛点。但 inactive 模式的调度优先级归零（Idle），意味着有实时更新需求的组件不适合用 inactive，应该用 hidden。

0x08-08. React Server Components 的 Streaming 性能优化——Sub-100ms TTFB 的生产模式

难度：⭐⭐⭐⭐（专家）
问题：React Server Components + Streaming 如何实现 <100ms TTFB？有哪些性能瓶颈？

标准答案：
RSC + Streaming 的核心是渐进式 HTML 流——服务端将 RSC Payload 以 Chunk 形式发送到浏览器，浏览器在收到第一个 Chunk 后就立即开始渲染（Suspense 边界）。优化目标是使 First Chunk（包含 App Shell）在 100ms 内到达浏览器。关键优化手段：Partial Prerendering（PPR，Next.js 15+）——将页面的静态部分（导航栏、侧边栏）在构建时预渲染为静态 HTML，动态部分（数据、个性化内容）在请求时流式填充。PPR 将 TTFB 中静态部分的渲染时间（通常 50-100ms）全部消除。

深入思考：

  • Nested Suspense Orchestration：Streaming 性能的关键是 Suspense 边界的设置。<Suspense fallback={<Skeleton />}> 包裹每个数据获取点，但 Suspense 嵌套层级过深（3 层以上）会导致 streaming 效率下降——因为内层 Suspense 需要等待外层 Suspense 的边界 resolution 后才能开始 stream。最佳实践：将数据获取尽量扁平化（1-2 层 Suspense 嵌套），利用 use()（React 19 的 Suspense-enabled hook）在 Server Component 中等待 Promise resolve。
  • Payload Chunking 策略：RSC 的 streaming Payload 不是整页发送的，而是逐步发送每个已 resolved 的 Chunk。Chunk 大小影响 TTFB——如果第一个 Chunk 太大（包含太多 CSS/JS 引用），TTFB 会变慢。Next.js 15 的 PPR 策略：第一个 Chunk 只发送 App Shell 的 HTML + 最优先的 CSS（critical CSS inline），动态部分的 Chunk 稍后发送。
  • CDN 与 Streaming 的冲突：Streaming 依赖 HTTP/1.1 的 chunked transfer encoding 或 HTTP/2 的 server push，但 CDN（Cloudflare、Akamai、CloudFront）默认会缓冲整个响应再转发——这会破坏 Streaming。解决方法：使用 CDN 的 streaming 模式（Cloudflare 的 streaming 响应，CloudFront 的 response-headers-policy 设置 X-Accel-Buffering: no）。

面试金句：

RSC Streaming 不是「把整页 SSRed 之后流式传输」——它是「先发送 App Shell，然后在 Suspense 边界解析时逐个发送 Chunk」。PPR 将这一模式推向极致——在构建时就决定哪些部分是静态的（直接预渲染到 HTML），哪些是动态的（请求时流式传输），从而实现了 <100ms TTFB。

0x08-09. React 19.2 与 React Native 0.83：统一的双平台发布与 Activity 组件

  • React 19.2 Activity 组件：React 19.2 引入了 <Activity> 组件（实验性），解决了一个长期存在的 React 痛点——组件的「活跃性」管理。<Activity> 是一个内置组件，允许开发者声明某个子树「是否活跃」——当 mode="hidden" 时，该子树仍然保持挂载状态（状态不丢失）但不渲染到屏幕上。这与 CSS display:none 不同——<Activity mode="hidden"> 让子树保持内存中的状态但跳过渲染，适用于标签页切换、后台任务、Keep-Alive 页面等场景。类似 Vue 的 <KeepAlive> 或移动端的 UIScene 管理。

0x0A React 19.2 新特性与 SSR 行为变化

0x0A-01. React 19.2 新增了哪些 React 层特性？useEffectEvent、cacheSignal 与 Performance Tracks 各解决什么问题？

标准答案：React 19.2 于 2025 年 10 月 1 日发布，官方说明它是过去一年内的第三个版本，前两个分别是 2024 年 12 月的 React 19 与 2025 年 6 月的 React 19.1。在 React 层新增了三项值得关注的能力。useEffectEvent 用于把 Effect 中的非响应式逻辑抽成稳定的 event 函数，从而不必把这类逻辑写进依赖数组。cacheSignal 仅用于 React Server Components，用来得知 cache() 的生命周期何时结束；它可以和 fetch 组合使用，例如对 fetch 做 cache() 包装后，在请求中传入 { signal: cacheSignal() }。Performance Tracks 为 Chrome DevTools 的 performance profile 增加一组自定义 track，其中 Scheduler 子 track 会展示 React 针对 blocking、transition 等不同优先级所做的工作，以及等待其他优先级或等待 paint 的情况。
深入思考：

  • 边界情况：cacheSignal 明确只适用于 React Server Components，客户端组件不能把它当成通用的请求取消机制，否则会得到错误的心智模型。
  • 机制层面：useEffectEvent 的价值在于区分「响应式依赖」与「非响应式读取」。Effect 仍然依赖它真正需要响应的值，而事件函数负责读取最新值，这减少了把无关值塞进依赖数组导致的重复执行。
  • 生产经验：Performance Tracks 把调度器的等待行为可视化，适合排查「交互卡顿但说不清卡在哪个优先级」的问题。团队可以把它纳入性能排查手册，先看 Scheduler track 是否出现长时间等待或优先级反复切换，再定位具体组件。
  • 对比延伸：三项新能力分别面向 Effect 依赖管理、RSC 缓存生命周期与调度可观测性，说明 19.2 的增量集中在「让既有模型更可控」，而不是引入新的编程模型。

生产踩坑案例：

  • 场景：某团队在项目里统一封装请求工具，并希望借助 cacheSignal 在服务端请求取消时释放资源。
  • 症状：部分客户端组件中调用该信号后行为异常，开发环境与生产环境表现不一致；同时 Effect 频繁重复执行，接口被重复调用。
  • 根因：把仅适用于 RSC 的 cacheSignal 当成通用取消机制使用；同时 Effect 的依赖数组里塞入了非响应式逻辑读取的值，导致每次渲染都触发重新订阅。
  • 修复：仅在服务端组件内配合 cache() 使用该信号；把 Effect 中的非响应式逻辑抽成 useEffectEvent 事件函数并重新梳理依赖数组；通过 Performance Tracks 确认重复渲染与优先级等待已经消失。
  • 教训：新 API 的适用范围就是它的边界，忽略「仅用于 RSC」这类限定会把正确工具用错场景；遇到渲染频率问题时，先区分响应式与非响应式依赖，再考虑在调度层做优化。

0x0A-02. React DOM 的 Partial Pre-rendering 是什么？如何与 prerender 和 AbortController 配合？

标准答案：Partial Pre-rendering 是 React 19.2 在 React DOM 层新增的能力，用于提前预渲染应用的一部分，之后再恢复渲染。典型做法是把静态部分预渲染后由 CDN 提供，用户访问时再恢复渲染 shell，把动态内容填入。官方给出的用法是先以 AbortController 调用 prerender，也就是说预渲染阶段本身是可中止的，预渲染完成后再进入恢复渲染阶段。
深入思考：

  • 边界情况：预渲染产物承载的是静态部分，动态内容仍然要在恢复渲染阶段生成；因此不能把 Partial Pre-rendering 理解成「把整个页面都缓存成静态」。需要明确哪些片段可以预渲染、哪些必须留到恢复阶段填充。
  • 机制层面：把静态外壳放到 CDN、在恢复阶段补齐动态内容，本质上是把渲染拆成两个可分离的阶段。这要求路由与数据层能够表达「哪些数据在预渲染阶段可用、哪些要等到请求时」，否则静态部分与动态部分会互相牵制。
  • 对比延伸：与整页静态化相比，Partial Pre-rendering 保留了动态内容的实时性；与完全动态渲染相比，它降低了首屏对源站的依赖。取舍点在于预渲染片段的划分粒度与新鲜度要求。
  • 生产经验：落地时先用 AbortController 管住预渲染任务的生命周期，避免构建阶段出现无法中断的长任务；同时为静态片段与动态片段分别建立缓存与回源指标，防止 CDN 缓存把本应实时的内容一起固化。

生产踩坑案例：

  • 场景：某团队希望降低内容站首屏的源站压力，尝试把大部分页面预渲染后交给 CDN。
  • 症状：上线后部分用户看到过期的动态内容，构建阶段偶发长时间无法结束的预渲染任务。
  • 根因：预渲染片段与动态片段的边界没有划清，把依赖请求时数据的内容也纳入静态外壳；同时预渲染任务没有通过 AbortController 控制生命周期。
  • 修复：重新划分可预渲染的静态部分，把动态内容保留到恢复渲染阶段；为 prerender 调用接入 AbortController，并分别监控静态缓存命中与动态回源。
  • 教训：Partial Pre-rendering 的收益来自边界清晰的静态/动态拆分，粒度划错会把「更快」变成「更旧」；预渲染属于构建任务，必须像其他构建步骤一样可中止、可观测。

0x0A-03. React 19.2 有哪些值得注意的行为变化？SSR Suspense、Web Streams、eslint 插件与 useId 前缀分别怎么理解？

标准答案：19.2 包含若干行为层面的变化。SSR 中 Suspense 边界改为批量揭示：此前 Suspense 边界在客户端渲染与服务器流式渲染下的揭示行为不一致，19.2 起 React 会在短时间内批量揭示服务端渲染的 Suspense 边界，让更多内容一起出现，从而与客户端渲染行为对齐。Node 上的 SSR 支持 Web Streams。eslint-plugin-react-hooks 升级到 v6。此外，默认的 useId 前缀发生变化。
深入思考：

  • 机制层面：Suspense 边界批量揭示改变的是服务端流式渲染的节奏，而不是边界的划分方式；它让服务端与客户端在揭示行为上更接近，但边界设计仍需按视觉区域和依赖关系来确定。
  • 边界情况：默认 useId 前缀变更是最容易影响测试与快照的变化。依赖固定前缀做字符串匹配或把前缀写进快照的测试需要同步更新，否则升级后会出现与业务无关的失败。
  • 生产经验：eslint-plugin-react-hooks 升级到 v6 后，规则集可能产生新的告警或错误。应在升级时单独观察 lint 输出，把新报出的 Hook 依赖问题当成真实问题处理，而不是直接关闭规则。
  • 对比延伸：Node SSR 支持 Web Streams 让服务端渲染的流式接口与 Web 标准对齐，减少 Node 流与 Web 流之间的适配代码；它与 Suspense 边界的揭示行为一起，构成 19.2 在服务端渲染方向上的两项改进。

生产踩坑案例：

  • 场景：某团队把项目从 React 19.1 升级到 19.2，CI 中既有单元测试也有基于快照的渲染断言。
  • 症状：升级后部分快照测试失败，lint 阶段出现新的 Hook 规则告警，页面上 Suspense 区域的展现时机与之前不同。
  • 根因：默认 useId 前缀变化导致快照中的 id 与旧值不一致；eslint-plugin-react-hooks v6 带来新的规则判定；SSR 下 Suspense 边界改为批量揭示，使流式输出的时机发生变化。
  • 修复：更新受前缀影响的快照与断言，按 v6 规则修正 Hook 依赖问题，并针对流式渲染把断言从「逐块到达顺序」改为「内容最终一致」。
  • 教训：升级小版本也要把「行为变化」与「API 变化」分开评估；快照与流式断言是最容易受影响的测试资产，应优先回归。
