后端面试题：Spring Boot 面试全解

发表于 2026-06-07 更新于 2026-09-08 分类于 后端

Spring Boot 高级面试全解，覆盖自动配置原理、Starter 机制、Actuator 监控、性能调优和常见生产踩坑。面向高级研发，侧重源码理解和架构设计。

0x00 自动配置与条件装配

0x00-01. Spring Boot 自动配置是怎么生效的？

标准答案：启动类上的 @SpringBootApplication 组合了 @SpringBootConfiguration、@EnableAutoConfiguration 和 @ComponentScan。@EnableAutoConfiguration 导入自动配置选择器，读取候选配置类，再依据 @ConditionalOnClass、@ConditionalOnMissingBean、@ConditionalOnProperty 等条件注册 Bean；它不是无条件把所有 Starter 的 Bean 都创建出来。

面试追问：排查时优先看 --debug 的 Condition Evaluation Report，确认“匹配成功/失败的条件”和实际生效的配置，而不是猜某个 Starter 是否加载。

0x00-02. @ConditionalOnMissingBean 为什么既能扩展又可能埋坑？

标准答案：它允许用户 Bean 优先：自动配置只在容器中没有目标类型或名称的 Bean 时提供默认实现。问题在于条件判断发生在配置解析阶段，多个自动配置之间存在顺序和类型匹配边界；用户自定义 Bean 可能意外覆盖默认实现，或者因为条件未匹配导致缺少 Bean。

生产边界：自定义自动配置应限制条件范围，给关键 Bean 写 @ConditionalOnClass、@ConditionalOnProperty 和明确的 @ConditionalOnMissingBean，并用应用上下文测试验证启用、禁用和覆盖三种路径。

0x01 Starter 与配置绑定

0x01-01. Starter、自动配置和业务代码分别负责什么？

标准答案：Starter 主要负责依赖聚合；自动配置负责根据 classpath、配置和现有 Bean 组装默认能力；业务代码负责显式声明业务 Bean 和覆盖点。三者不能混为一谈：引入 Starter 不等于功能一定启用，还要满足条件和配置。

0x01-02. @ConfigurationProperties 和 @Value 怎么选？

标准答案：少量、一次性配置可用 @Value；一组有层级、需要校验和复用的配置优先 @ConfigurationProperties，配合 @Validated 在启动期失败。配置应区分默认值、环境覆盖、敏感信息来源和动态刷新边界，密码、Token 不应写入仓库。

0x02 Web、Actuator 与可观测性

0x02-01. Actuator 暴露端点时最容易忽略什么？

标准答案：management.endpoints.web.exposure.include 只控制暴露范围，不等于端点已经安全。生产环境应通过独立管理端口或网络策略限制访问，对 env、beans、heapdump 等敏感端点谨慎开放，并把健康检查分为存活与就绪，避免依赖故障导致实例被错误重启。

0x02-02. Spring Boot 启动慢怎么定位？

标准答案：先用启动耗时指标和 Condition Evaluation Report 定位自动配置、Bean 初始化、外部连接和类路径扫描，再区分“启动慢”与“首请求慢”。可对非关键 Bean 使用懒加载，但必须补齐首请求延迟、就绪探针和超时验证；不能用全局懒加载掩盖循环依赖或错误的远程调用。

0x03 版本升级与生产排障

0x03-01. Boot 2 升 Boot 3 需要重点检查什么？

标准答案：重点检查 Java 基线、javax.* 到 jakarta.* 的迁移、Spring Security 配置、Hibernate 版本、路径匹配和自定义 Starter 的条件类。升级应先做编译与上下文测试，再做接口、序列化、数据库迁移和灰度流量回归。

0x03-02. 配置不生效如何建立证据链？

标准答案：记录配置来源优先级、最终绑定值、激活 profile、条件评估结果和实际 Bean。对敏感值只记录哈希或存在性；用最小复现和应用上下文测试确认问题属于配置覆盖、条件未满足、绑定失败还是运行时刷新边界。
